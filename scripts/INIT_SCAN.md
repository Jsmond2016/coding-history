# Git 仓库初始化扫描指南

## 概述

初始化扫描脚本用于首次导入 Git 仓库的历史提交数据到数据库。该脚本支持：

- ✅ **自定义时间范围**：可配置扫描 3/6/12 个月的历史数据
- ✅ **分阶段扫描**：按周为单位分批扫描，避免一次性加载过多数据
- ✅ **断点续传**：支持中断后从上次位置继续扫描
- ✅ **自动去重**：基于 commit hash 自动过滤重复提交
- ✅ **详细日志**：实时显示扫描进度和统计信息

## 使用方法

### 1. 基础用法

```bash
# 在项目根目录执行
pnpm init-scan
```

默认扫描最近 **3 个月**的提交记录。

### 2. 自定义时间范围

```bash
# 扫描最近 6 个月
pnpm init-scan -- --months 6

# 扫描最近 12 个月（1 年）
pnpm init-scan -- --months 12

# 扫描最近 24 个月（2 年）
pnpm init-scan -- --months 24
```

**注意**：`--` 是必需的，用于将参数传递给底层脚本。

### 3. 在 backend 目录执行

```bash
cd backend
pnpm init-scan           # 扫描 3 个月
pnpm init-scan --months 6  # 扫描 6 个月
```

## 工作流程

### 首次扫描

1. **读取配置**：从数据库读取仓库配置（如果数据库中没有配置，会尝试从 `backend/config/repositories.json` 读取并迁移）
2. **同步仓库信息**：确保数据库中的仓库配置是最新的
3. **分阶段扫描**：
   - 将时间范围分割成多个 **1 周** 的阶段
   - 逐周扫描提交记录
   - 每完成一周，更新数据库中的扫描进度
4. **自动去重**：插入前检查 commit hash，跳过已存在的提交
5. **统计汇总**：显示扫描结果统计

**注意**：配置已迁移到数据库，推荐使用前端配置管理页面进行配置。扫描脚本会优先使用数据库中的配置。

### 断点续传

如果扫描过程中被中断（如服务崩溃、手动停止），再次运行脚本时：

1. **检查进度**：读取数据库中的 `initialScanToDate` 字段
2. **继续扫描**：从上次完成的日期继续，而不是从头开始
3. **避免重复**：已扫描的周会被跳过

示例日志：

```
[扫描仓库] Monkey SaaS Web
  路径: /Users/xxx/Code/monkey-saas-web
  继续扫描: 从 2024-10-15 继续  ← 从上次中断位置开始
  目标日期: 2024-08-21
```

## 配置说明

### 仓库配置

**推荐方式**：使用前端配置管理页面进行配置（配置存储在数据库中）

**旧配置文件方式**（仅用于迁移）：

位置：`backend/config/repositories.json`

```json
{
  "author": {
    "email": "your-email@example.com"
  },
  "repositories": [
    {
      "id": "my-project",
      "name": "My Project",
      "path": "/absolute/path/to/repo",
      "enabled": true
    }
  ]
}
```

- `enabled: false` 的仓库会被跳过
- `author.email` 用于过滤提交记录（只扫描该作者的提交）

**注意**：如果数据库中没有仓库配置，扫描脚本会尝试从配置文件读取并自动迁移到数据库。

### 数据库字段

`repositories` 表中的 `initialScanToDate` 字段记录扫描进度：

- `null`：未开始扫描
- `1697299200000`：已扫描到该时间戳（毫秒）

## 常见问题

### Q: 扫描需要多长时间？

**A**: 取决于：
- 仓库大小和提交数量
- 时间范围（3/6/12 个月）
- 网络和磁盘性能

参考：1000 条提交约需 1-2 分钟。

### Q: 可以同时扫描多个仓库吗？

**A**: 脚本会串行扫描所有启用的仓库，确保稳定性。

### Q: 如何重新扫描某个仓库？

**A**: 手动删除数据库中该仓库的记录：

```sql
-- 删除提交记录
DELETE FROM commits WHERE repo_id = 'your-repo-id';

-- 重置扫描进度
UPDATE repositories SET initial_scan_to_date = NULL WHERE id = 'your-repo-id';
```

然后重新运行 `pnpm init-scan`。

### Q: 扫描失败怎么办？

**A**: 脚本会：
1. 记录错误日志
2. 保存当前进度
3. 继续扫描下一个仓库

再次运行脚本会从失败的阶段重新开始。

### Q: 如何验证扫描结果？

**A**: 
1. 查看日志中的统计信息
2. 启动 Web 服务查询数据：
   ```bash
   pnpm dev:backend
   pnpm dev:frontend
   ```
3. 在前端页面查看提交记录

## 最佳实践

1. **首次使用**：建议先扫描 3 个月数据，验证无误后再扫描更长时间
2. **大型仓库**：对于超过 10000 条提交的仓库，建议分批扫描（先 3 个月，再 6 个月）
3. **定期备份**：扫描完成后备份数据库文件 `backend/database/git-statistics.db`
4. **监控日志**：留意 `[阶段 X 失败]` 日志，及时处理异常

## 与 Web 服务的关系

- **初始化扫描**（`pnpm init-scan`）：一次性导入历史数据
- **Web 服务**（`pnpm dev:backend`）：
  - 启动时不再自动扫描
  - 提供 API 查询已导入的数据
  - 定时任务每天增量扫描新提交

**推荐流程**：

```bash
# 1. 首次使用：初始化历史数据
pnpm init-scan

# 2. 启动 Web 服务
pnpm dev:backend
pnpm dev:frontend

# 3. 访问前端页面查看数据
open http://localhost:35173
```

## 技术细节

- **分阶段策略**：每周一个阶段，避免 Git 命令超时
- **去重机制**：基于 `commitHash` 字段的唯一索引
- **断点存储**：每完成一周更新 `initialScanToDate`
- **错误恢复**：失败时保存进度到当前阶段起始日期
- **并发控制**：串行扫描，避免 Git 仓库锁冲突
