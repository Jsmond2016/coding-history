## 2. 待处理问题清单

### 2.1 「为什么没有扫描入库？」（根因未定论）

可能方向（需你本地/环境逐项排除）：

- 统计页是否**手动触发过扫描**，或是否存在**已到期的定时任务**；扫描区间是否覆盖目标日期。
- 该仓库在系统中是否**启用**，路径是否指向当前机器上真实存在的目录。
- **作者过滤**：扫描侧只认仓库配置里的**作者邮箱**；若 Git 提交作者邮箱与配置不一致，会被整段过滤掉（与统计页「按作者筛选」无关）。
- 后端日志 / 扫描状态接口：是否有报错、`git pull` 失败、权限问题等。

**待办**：在你常用的环境里跑一遍「配置核对 + 一次覆盖区间的扫描 + 查库/API」，把结论写回本节或关单。

### 2.2 忽略分支 + 去重 + `branch` 与业务直觉不一致（已知实现行为）

你的预期大致是：

- 忽略 `develop` / `master` / `uat` 后，**仍在其他分支上的提交**应能入库并在统计里看到。
- 若未上线，代码在 feature 等分支；若已上线，会在 `release`（或类似）上——**即使按 hash 去重，也应有一条可查记录**。

**当前实现要点**（详见 [requirements.md §2.7.7](./requirements.md)）：

- 忽略分支是在**查询阶段**过滤：若某行记录的 `branch` 字段落在忽略列表里，该提交在列表/统计中**不展示**。
- 同一 `repoId + commitHash` **只保留一行**；若该提交**第一次**扫描时记在 `develop`（且 `develop` 被忽略），之后即使同一 commit 已出现在 `release`，**当前实现通常不会把 `branch` 更新为 `release`/null**，则该记录可能**一直被忽略规则挡掉**。

**待办**（产品/技术）：

- 是否接受上述行为作为「已知限制」仅文档化，还是要在实现上改为：**合并进 release/master 后更新或清空 `branch`**、或**展示时按「是否可达 release」重算**等（可与 §8.1 优化项对齐）。
- 若 `release` 分支**从未被纳入扫描分支集合**，也可能导致永远拿不到「上线后」的那条语义，需结合 `GitScanService` 实际扫描分支列表核对。
